One high-level spec goes in: a function, its constraints and what to optimise. The agent's job is to take that spec down a ladder of ever more faithful, ever more expensive models of the hardware, keeping only the candidates worth the next level's cost, and checking each level against the golden model before trusting it.

## The ladder

Each level offers its own power, performance and area trade-offs, and each costs more per design than the one above it. Exploring cheaply at the top is what makes it affordable to be thorough at the bottom.

<LadderTable column="ppa" />

At the vendored commit all four milestones are done and every level of the ladder is live: spec intake (L0), analytical exploration (L1), system-level simulation in SimPy and the cycle-accurate model (together the repository's L2, milestone 3), RTL simulation (L3), synthesis (L4), gate-level simulation of the netlist, synthesis on a second target, an ASIC on the open sky130 PDK (milestone 4), and back-annotation (L5). The ASIC rung is **post-synthesis only**: there is no place and route, and its numbers are an open-PDK estimate, not silicon. Exploration itself still happens at L1, where a design costs microseconds to score; the lower levels check, measure and correct what L1 chose.

## The graph, replayed

The agent is a LangGraph `StateGraph`. `intake` turns the spec into a validated `Spec`; `confirm_spec` stops for a human with `interrupt()`; `propose` asks the LLM for a plan; `explore_family` runs once per family, fanned out in parallel with `Send`, each branch an Optuna NSGA-II study inside the box the LLM chose; `analyse` merges the results, computes the Pareto front and its hypervolume, shows the LLM a compact summary and asks what next. Code then applies hard rules the LLM cannot override: the round cap, the budget, and no "infeasible" verdict while feasible designs exist. After `select`, milestone 2's graph adds `back_annotate`: the selected design's estimates against any measured synthesis data, and a flag if the winner would change. Milestone 3 adds two more nodes, both code only: `l2_simulate` before it, which simulates every L1-feasible design of the run inside the spec's system and re-selects on the simulated numbers, and `l5_reexplore` after it, which re-explores around the measured designs under the refit cost model when a measurement flags a winner change. Milestone 4 adds a third, `l2_feedback`, also code only: when L2 rejects every L1-feasible design, it corrects the L1 bound from the simulations and re-explores (below). It also lets a spec name its target: the same graph explores an ASIC spec with an ASIC cost model and an ASIC system prompt, and the FPGA prompt stays byte for byte what it was.

Milestone 2 also changed how the agent spends its budget, to map the whole trade-off curve and not only the corner the spec's selection rule cares about. The LLM gained a `map_front` decision, which asks code for a front-mapping round: NSGA-II over the ranges of the families on the front so far. And 40% of the budget is held in reserve: before a run stops, code spends whatever is left on one final front-mapping round, with no LLM call.

## L2: the design inside its system

A throughput figure says how fast a design is on its own. A system asks something harder: 32 requests arriving at once on every control tick, bursts of 8 from a sensor front end, a DDS that stalls when its FIFO fills. Milestone 3 adds that rung. Every family obeys one interface contract (ready, valid, a latency and an initiation interval), which the generated RTL implements and the formal checks pin down; a cycle-accurate model implements the same contract, and SimPy models put it inside three systems: a DDS feeding a mixer, a control loop and a bursty request stream. Each design runs on its own clock at its estimated Fmax <Prov kind="estimate" />, so every system number is <Prov kind="simulated" />.

During exploration, L1 screens a system constraint with an analytic bound that is optimistic by construction (each burst or tick served alone, starting on a clock edge), so L1 never discards a design L2 would accept. After `select`, L2 simulates every L1-feasible design the run evaluated and re-selects. That is cheap: the <V of="designs" fmt="int" /> designs share only <V of="m3.gt.tuples" fmt="int" /> distinct combinations of latency, initiation interval and Fmax, and the simulation is cached on them, which is also how the repository computes an exhaustive simulated ground truth for each system spec.

Here is the spec where it matters. `multiaxis_control` asks for all 32 results of every 1 µs tick within 0.44 µs. Read in milestone-2 terms (throughput at the average rate, 32 MSPS) the best design is `pipelined_m` m=7 (<V of="m3.multi.msps_lf" fmt="int" /> LUT+FF); the L1 bound picks m=5 (<V of="m3.multi.bound_lf" fmt="int" />); the simulation picks m=4 (<V of="m3.multi.true_lf" fmt="int" />). m=4 and m=5 have the same numerics, and m=5 is smaller, so m=4 is _dominated_ in the L1 objectives: L2 has to look at every L1-feasible design, not only the L1 front. The first version of the `l2_simulate` node shortlisted from the front and could never reach m=4; the planner's review found it before the merge. Even sizing for the peak rate (32 requests in 0.44 µs, <V of="m3.multi.peak_floor" fmt="f1" /> MSPS) stops at m=5, so only the simulation gets to m=4, by a margin of <V of="m3.multi.miss" fmt="pct" />. The model aligns each request to the next CORDIC clock edge but has no synchroniser: a real clock-domain crossing would add about two destination cycles, which against that margin could move the winner again. The repository lists it as a limitation.

## A second target: an ASIC on sky130

The flow (<V of="m4.cal.tool" fmt="str" />) runs it against the open `sky130_fd_sc_hd` library at its typical corner (25 °C, 1.80 V) with a <V of="m4.cal.clock_ns" fmt="int" /> ns clock: cell area, flip-flops, the register-to-register path with the library's wire-load model, and vectorless power <Prov kind="measured" />. ## L2 → L1 feedback

L1's system bound is optimistic by construction. If L2 rejects **every** L1-feasible design of a run, the run spent its budget where the bound was wrong. The `l2_feedback` node then does for the bound what L5 does for the cost model: it measures the bound's error on every simulated design, fits a monotone correction in the design's utilisation per contract class (never more optimistic than any simulation it has seen, so labelled an empirical estimate), and re-explores with a separate budget of 3 × 60 evaluations under the corrected bound.

On the committed specs it never fires: 0 of <V of="m4.fb.recorded" fmt="int" /> recorded searches and 0 of <V of="m4.fb.live" fmt="int" /> live runs found an L1-feasible set that L2 rejected whole. So the repository constructed a spec where it does (bursts of 32 requests at 130 MS/s, a 130 MS/s throughput floor, p99 within 0.4 µs). It fired in <V of="m4.fb.fired" fmt="int" /> of <V of="m4.fb.searches" fmt="int" /> searches, all random search, and recovered a passing design in <V of="m4.fb.recovered" fmt="int" /> of <V of="m4.fb.fired" fmt="int" />; the same extra budget with the uncorrected bound recovered <V of="m4.fb.uncorrected" fmt="int" />. Evidence for the mechanism, on three cases; the [results](/results#feedback) have every search.

## An optional outer loop: the campaign agent (experimental)

Milestone 3 also tried a different kind of agent on top. A campaign agent, built on LangChain's Deep Agents harness (planning to-dos, a virtual file system, one sub-agent for the ladder, cross-run memory in a LangGraph Store), is meant for long-horizon work: take specs down the whole ladder, re-plan when a measurement changes the winner, carry lessons from one spec to the next. The structured graph stays the inner loop and is one of its tools (`run_dse`); the others are `explore_family`, `simulate_system`, `verify_rtl`, `synthesize`, `back_annotate`, `reexplore`, `finalize`, `recall` and `remember`. Code enforces the same 400 L1 evaluations per spec, refuses to finalise a system spec on L1 bounds or a flagged winner change that has not been re-explored, and stops a campaign after 40 model calls or four identical tool calls in a row.

It is **experimental**: optional, off by default, and used by nothing in the structured graph or the command line. The repository measured it in an A/B against the structured graph and found no gain at a higher cost, which the [results](/results#ab) show in full.

## Many agents at once

There are three kinds of parallelism. Inside a run, `Send` fans `explore_family` out across the families the LLM chose, so the studies run side by side and a reducer merges their evaluations. Across runs, every run is an independent graph with its own SQLite checkpoint, so runs can be queued and run side by side, and a run interrupted for human input, or killed, resumes from its last completed step. And since milestone 4, several graphs can work on one spec as a fleet <LevelBadge status="live" milestone="M4" />.

### The fleet: orchestrated by code

Milestone 3's lesson was that an LLM in the outer loop adds cost and loops without adding search. So the fleet puts **code** between the graphs. Two members, one per contract class (the FSM families and the pipelined families), each an unchanged structured graph restricted to its families, with its own LLM architect. Phase 1 splits half the budget equally; every evaluation goes to a shared LangGraph Store; code computes per-family lessons from the Store (counts and best values, nothing an LLM wrote), gives the other half to the members in proportion to their share of the merged Pareto front, and seeds each phase-2 study with the Store's front designs of its family. Code merges, selects and runs L2 once.

**Why no LLM coordinator?** Its decisions here are a budget split and a front merge: arithmetic over numbers code already has. Milestone 3's A/B showed what an LLM in that seat costs (<V of="m3.ab.cost_ratio_min" fmt="f2" />–<V of="m3.ab.cost_ratio_max" fmt="f2" />× as much per spec, for no gain), and its free-text notes into the inner architect narrowed the first box in its worst run. In the fleet there is no channel for free text at all. Code also enforces the equal budget: the fleet never spends more than the 400 L1 evaluations a single graph gets, so the two can be compared.
