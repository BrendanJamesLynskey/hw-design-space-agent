One high-level spec goes in: a function, its constraints and what to optimise. The agent's job is to take that spec down a ladder of ever more faithful, ever more expensive models of the hardware, keeping only the candidates worth the next level's cost, and checking each level against the golden model before trusting it.

## The ladder

Each level offers its own power, performance and area trade-offs, and each costs more per design than the one above it. Exploring cheaply at the top is what makes it affordable to be thorough at the bottom.

<LadderTable column="ppa" />

At the vendored commit, milestones 1 and 2 are done: spec intake (L0), analytical exploration (L1), RTL simulation (L3), synthesis (L4), gate-level simulation of the netlist and back-annotation (L5) are live. System-level (SimPy) and cycle-level simulation are planned for milestone 3, and nothing on this site animates a planned level as if it had run. Exploration itself still happens at L1, where a design costs microseconds to score; the lower levels check, measure and correct what L1 chose.

## The design principle: the LLM never produces a number

The LLM chooses which architecture families to explore, over which parameter ranges, and what to do after each round. Code computes every figure. That rule is in the system prompt every recorded call was sent:

Each LLM call names a Pydantic schema (`ExplorationPlan`, `AnalysisDecision`), and those schemas have no field for a LUT count, an Fmax or an error figure: the model can name families, ranges, a budget split, a decision and its reasons, and nothing else. ## The graph, replayed

The agent is a LangGraph `StateGraph`. `intake` turns the spec into a validated `Spec`; `confirm_spec` stops for a human with `interrupt()`; `propose` asks the LLM for a plan; `explore_family` runs once per family, fanned out in parallel with `Send`, each branch an Optuna NSGA-II study inside the box the LLM chose; `analyse` merges the results, computes the Pareto front and its hypervolume, shows the LLM a compact summary and asks what next. Code then applies hard rules the LLM cannot override: the round cap, the budget, and no "infeasible" verdict while feasible designs exist. After `select`, milestone 2's graph adds `back_annotate`: the selected design's estimates against any measured synthesis data, and a flag if the winner would change.

Milestone 2 also changed how the agent spends its budget, to map the whole trade-off curve and not only the corner the spec's selection rule cares about. The LLM gained a `map_front` decision, which asks code for a front-mapping round: NSGA-II over the ranges of the families on the front so far. And 40% of the budget is held in reserve: before a run stops, code spends whatever is left on one final front-mapping round, with no LLM call.

Three things to look for. On the infeasible spec, the LLM itself returns `infeasible` and names throughput as the binding constraint; code only checks that no feasible design exists before accepting it. In M1 the last word was often code's: the LLM asked to `refine`, the hypervolume gained less than 1% that round, and that rule stopped the run early, which is why the M1 agents mapped less of the front than NSGA-II. In M2, watch for `map_front` and for the final round planned by code: that is how the agents closed the gap, as the [results](/results) show.

## Many agents at once

There are two kinds of parallelism. Inside a run, `Send` fans `explore_family` out across the families the LLM chose, so the studies run side by side and a reducer merges their evaluations. Across runs, every run is an independent graph with its own SQLite checkpoint, so runs can be queued and run side by side, and a run interrupted for human input, or killed, resumes from its last completed step. That is what makes a fleet of agents running 24/7 possible, each evaluating a real design decision. Each eval was a small fleet:
